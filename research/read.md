Ооо, да! 😸 Причём тут можно сделать довольно интересный инженерный проект: разобраться, как TinyPNG сжимает изображения, и реализовать собственный аналог на Python.

Но есть нюанс: алгоритмы TinyPNG — закрытая реализация. Мы не сможем достоверно восстановить их исходный код только по результатам сжатия. Зато можем исследовать поведение сервиса экспериментально и построить алгоритм, который даст похожие результаты.

## Как я бы подошла к реверс-инжинирингу

Я бы не стала просто подключать готовую библиотеку и называть это аналогом TinyPNG. Лучше провести серию экспериментов.

1. Подготовить набор изображений: фотографии, скриншоты, иллюстрации, логотипы, прозрачные PNG.
2. Прогнать их через TinyPNG.
3. Сравнить исходники и результаты: размер, цветовые палитры, PNG chunks, метаданные, PSNR, SSIM, perceptual similarity.
4. Проверить, как меняется результат при разных типах изображений.
5. Реализовать несколько вариантов алгоритма и сравнить с TinyPNG.

## Что можно получить

Я бы целилась в сервис, который:

- Сжимает PNG, JPEG, WebP, AVIF.
- Автоматически определяет оптимальный алгоритм для изображения.
- Позволяет выбирать режим: максимальное сжатие или сохранение качества.
- Поддерживает пакетную обработку.
- Работает без отправки изображений сторонним сервисам.
- Имеет API для интеграции в приложения.

Самое интересное: можно попробовать сделать адаптивный компрессор, который сам определяет тип изображения и выбирает стратегию сжатия. Например, для скриншота — один алгоритм, для фотографии — другой, для аниме-иллюстрации — третий.

Я бы предложила начать с полноценного сравнительного эксперимента TinyPNG vs наш алгоритм на 100–200 изображениях. Так мы поймём, насколько близко реально можем подобраться к результатам TinyPNG, а не будем гадать по документации. 😼
